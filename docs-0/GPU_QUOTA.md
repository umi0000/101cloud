# 显卡配额怎么管：工作室版

## 1. 先说结论

**现在采用“共享显卡，但每人同时只能用一张”的方案。平台管分卡和记账，PVE 管容器，宿主机上的程序检查实际使用情况。用户容器里的程序不参与可信记账。**

必须分清两件事：

- **限制一个人能用几张卡：可以做，也应该做成硬规则。**
- **把一张 TITAN Xp 切成每人固定几 GB 显存、固定百分比算力：普通 PVE LXC 做不到。**

所以我们卖的是“单卡共享使用权”，不是“独占一张卡”，也不是“保证得到半张卡的性能”。本文是待实现方案，不是已经上线的功能。完整系统设计见 [ARCHITECTURE.md](ARCHITECTURE.md)。

## 2. 配额到底限制什么？

| 要管的东西 | 怎么管 | 能保证什么 |
| --- | --- | --- |
| 每人同时用几张卡 | 普通成员上限为 1，后端检查，宿主机限制实际设备访问 | 多开容器也拿不到第二张卡 |
| 一张卡共享给几个人 | 管理员设置共享人数上限，正在开机和正在回收的分配也算进去 | 不会因为多人同时申请而突破登记上限；不保证显存够用 |
| 一个人开几个实例 | 单独设置实例数、CPU、内存和磁盘额度 | 限制实例总量和主机资源；不等于共享 GPU 的性能隔离 |
| 一个人能用多少卡时 | 管理员可设置时长额度；宿主机确认使用和释放，额度耗尽后按规则通知、停止计算 | 能控制累计使用；停止是一个需要确认的过程，不是毫秒级掐断 |
| 每人最多几 GB 显存 | 当前只监控、做准入检查和提示，不作为硬配额出售 | **不能保证运行后不超过建议值** |
| 每人固定多少算力 | 当前不承诺 | **不能把两人共享说成每人固定 50%** |

这里的“共享人数上限”是管理员根据实际应用测试后设置的值，本文不给四张卡编一个未经验证的安全并发人数。

四卡规格只给明确授权的特殊用户。普通成员不能通过改网页请求，把单卡规格变成四卡。

## 3. 成员实际怎么用？

假设有四张卡，我们在界面上简称 A、B、C、D。

1. 小王点击“启动 GPU 工作空间”。
2. 平台检查小王是否已经在使用显卡。如果没有，再从状态正常、还有共享名额的卡里选择负载较低的一张。
3. 假设选中了 B。平台先登记，再让 PVE 在容器停止时配置设备，随后启动容器并检查是否正常。
4. 小王进入容器跑 Python、Jupyter 或训练程序，使用的是 B。其他成员也可能被分到 B，大家共享。
5. 小王点“释放显卡”，平台停止这个 GPU 容器，确认计算已经结束，再释放名额并结束这次计时。磁盘、代码、数据和固定 IP 保留，下次启动可以重新选卡。

**重要：当前“释放显卡”会停止 GPU 容器，里面的 SSH、Jupyter 连接会断开。不是容器一直开着、显卡可以随时无痛拔掉。**

选卡发生在 GPU 容器启动前。容器已经开着时，小王再敲一次 `python train.py`，不会重新选卡。想让每个命令启动前都重新调度，需要另做受管任务入口，不能假装 PVE 已经具备这个功能。

### 同一个人开两个 GPU 容器呢？

如果实例额度允许，两个容器必须复用小王当前的 B 卡，不能一个拿 B、另一个拿 C。

停止其中一个容器，不代表释放了小王的卡：只要另一个还在使用，登记和计时就继续。最后一个相关 GPU 容器停止并确认回收后，才结束小王的这次显卡使用。

这里管的是“每人一张物理卡”，不是“每人只能开一个程序”。同卡多个容器的 CPU、内存和磁盘仍分别占用实例额度。

## 4. 怎么防止用户绕过？

### 不是在网页上限制一下就完了

成员只提交“我要哪个套餐、启动哪个实例”。后端自己决定用哪张卡，并检查这个用户已经获得了哪些卡。

同一个人同时打开两个页面申请，也要按同一个用户串行核对。先在数据库里完成登记和额度检查，再操作 PVE，不能让两个请求各自判断“他现在没用卡”。

### 不是只设置一个环境变量

`CUDA_VISIBLE_DEVICES` 可以让程序使用方便，但用户能改它，**它不是安全锁**。

宿主机要限制这个容器真正能访问的 NVIDIA 计算设备，只开放分到的物理卡及所需控制设备。验收标准是：用户不能在未授权卡上申请显存、运行计算。

有些工具可能仍能看到其他卡的硬件信息。不能仅凭 `nvidia-smi` 显示几张卡来判断权限是否正确，要实际尝试访问未授权卡。

### 不是让容器里的小程序说自己用了多久

可信检查程序运行在 PVE 宿主机，由管理员维护，不在成员容器里面。

它从 NVIDIA 驱动读取 GPU 进程，再从宿主机判断进程属于哪个容器，最后对应到平台用户。容器里报来的用户名、进程名和“我已经停止”通知都不能当作收费依据。

默认使用非特权 LXC，不给成员宿主机权限、PVE 凭据或宿主机控制接口。在这个前提下，容器内 root 不能直接杀掉宿主机的记账程序。

## 5. 最容易误会的地方：一人一张，不是一人独占一张

一张 TITAN Xp 约有 12 GB 显存。共享时，成员会竞争这些显存。

举个例子：小王先占用了大部分显存，小李后来也被分到了这张卡。小李的程序可能因为剩余显存不足而报错。**“两个人都有单卡配额”不代表平台已经替两个人各留出一半显存。**

我们能做的是：

- 分配前看剩余显存，尽量避免把新用户塞到快满的卡上。
- 结合一段时间的负载、共享人数和已登记但尚未启动的实例选卡，不只看某一秒的利用率。
- 卡太满、人数达到上限或状态不明时，拒绝这次启动，让成员稍后重试。
- 显示每张卡的显存、负载和共享人数，方便成员判断。
- 若需要显存使用约定，明确标为建议值；对违反使用约定的处理提前告知，不能临时偷偷杀任务。

我们不能承诺的是：

- 启动检查通过后，其他人就不会继续申请显存。
- 在后台发现超量后再杀进程，就能避免其他成员先发生显存不足。
- 在 PyTorch 里设置显存比例，就能限制用户换个程序或改掉配置。
- 给容器限制 8 GB 系统内存，就等于把显存也限制成 8 GB。

**这不是面板没写好，而是当前“普通 LXC 直接共享 TITAN Xp”的资源边界就没有替我们完成显存切片。**

## 6. 卡时怎么记，用户杀程序有没有用？

### 记运行期间的使用权，不伪装成精确计算时间

从宿主机确认 GPU 工作空间运行且持有显卡访问权开始，到确认停止或确认释放为止，计算有效收费时间。确认实例停止后，CPU、内存、磁盘和GPU全部停止计费；GPU可以继续绑定并占用容量，不自动解绑或释放。再次确认运行后，恢复全部应计费资源。

运行期间即使利用率为零，只要工作空间仍持有使用权，就继续计时；确认停机后的保留绑定则不收费。停止请求失败、Agent失联或状态未知不能提前判为已停止；节点离线区间按显式offline政策处理。历史停机前费用保留，不自动追溯退款，未交付创建失败退款规则不变。

**不能只在 GPU 利用率大于零时收费。** 运行实例加载模型但没有计算时仍可能占显存；但确认停机后所有资源免费，与容量是否回收分开处理。

### 多个程序、多个容器，不重复计算同一张卡

小王的两个容器都在 B 卡上：

| 容器 | 使用时间 |
| --- | --- |
| 第一个 | 10:00—11:00 |
| 第二个 | 10:30—11:30 |

小王的 B 卡使用时间是 **10:00—11:30，共 1.5 个共享卡时**，不是把两个容器相加成 2 小时。两个容器自己的 CPU、内存和存储费用另算。

不同用户共享同一张卡时，各自记自己的共享使用时间。因此所有人的共享卡时之和，可能超过这张物理卡的实际开机时长。这是共享产品，不应写成独占物理卡时。

### 用户的这些操作不能影响主账

| 用户操作 | 平台怎么处理 |
| --- | --- |
| 杀掉容器内的启动器 | 不直接停表，继续核对 GPU 工作空间和后台计算 |
| 训练结束，但 GPU 容器还开着 | 按持有使用权继续计时；不凭利用率为零自动释放 |
| 暂停、冻结容器 | 不视为显卡已释放 |
| 实例确认停止 | 全部资源停止计费；GPU保持绑定并占用容量，再次确认运行后恢复应计费资源 |
| 点击释放，但后台任务还在跑 | 先核对真实结果；确认停止即可停止收费，容量只有明确移除并确认回收后才释放 |
| 直接调用接口说“我用完了” | 只视为释放申请，必须经过宿主机确认 |

启动前就要留下待确认记录，防止用户在容器启动项里快速跑完计算，而平台因为稍后核验失败就没有任何记录。时间不确定的部分保留证据、等待核对，不随意补收，也不删除事实。

宿主机程序把事件先保存在本地，再传给平台；重复上传不能重复扣费。平台或节点失联时标记待核对，不直接宣布卡空闲，也不能无期限继续自动扣钱。自动回收必须真正停止计算并经过确认。

### 卡时额度耗尽怎么办？

先阻止新申请，按已告知的政策提醒用户保存结果；宽限期结束后停止 GPU 计算容器并核验回收，保留磁盘数据。停止可能有延迟，实际区间需要记录，不能为了把账单凑成整数就伪造停止时间。

## 7. 如果确实想要“每人固定几 GB 显存”，怎么办？

| 选择 | 结果和代价 |
| --- | --- |
| 保留现有卡，继续普通共享 | 最简单，但不能保证显存硬配额，也不能保证固定算力 |
| 保留现有卡，需要大显存时改为整卡独占或预约 | 避免同一张卡上的其他成员争抢；同时使用的人数减少，仍不是硬件级安全隔离 |
| 更换支持 MIG 的具体型号，并适配分片分配 | 可以利用硬件显存/计算资源分片；不是随便换一张新显卡就支持 |
| 引入软件层显存限制 | 必须核验硬件、框架、兼容性和防绕过能力；不能只加一个可被容器 root 替换的库，就当成任意程序的可靠配额 |

TITAN Xp 不支持 MIG。MPS 或普通 GPU 时间共享也不能直接当作这批卡的硬件显存分区。当前不把这些额外方案作为上线前提，也不在没有验证时宣传“显存限制已经解决”。

## 8. 需要开发的东西，其实就是这几块

1. **用户额度**：每人最多几张卡、能开多少实例、能用多少共享卡时；四卡例外要明确授权。
2. **分卡登记**：记住谁正在用哪张物理卡，多个同卡实例复用同一项登记；并发申请不能钻空子。
3. **自动选卡**：启动前检查卡是否健康、是否太满、还有没有共享名额。
4. **PVE 设备配置**：容器停止时配置正确设备，启动后验证；不允许成员传任意设备路径。
5. **宿主机检查与记账**：不信任容器上报，核对实际进程和使用区间，处理停止失败、重启与失联。
6. **成员页面**：清楚显示正在用哪张卡、共享情况、累计时长，以及“释放会停止容器，数据保留”。

PVE 不会替我们完成每用户单卡限制、自动选卡和共享卡时账单，但它能承接容器、设备配置和启停。不要再重写一套虚拟化底座。

## 9. 怎么证明这套规则真管用？

上线前至少做这些实际测试，不能只看网页提示成功：

- 同一个用户同时发起两个申请，仍只能使用一张物理卡。
- 不同用户可以在同一张卡实际运行 CUDA 程序。
- 用户修改环境变量、绕过启动器，也不能在未授权卡上计算。
- 开两个同卡容器，重叠时间不重复计费；停止其中一个，不提前释放整个人的卡。
- 杀掉容器内程序不能修改宿主机账本；后台残留计算不能被算作已释放。
- 停止失败、Agent 失联或 PVE 重启时，不错误分配资源、不重复收费。
- GPU 容器停止后数据还在，重新启动能继续使用文件，但不承诺恢复未保存的计算现场。

**最后一句：现在能做实的是“能用几张卡、共享给几个人、用多久、怎么防绕过”。显存和算力仍然是共享资源，不能用一份配额表假装已经切好了。**
